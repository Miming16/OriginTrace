# 0.2.2 — Frontend Architecture & Component Hierarchy

**Scope:** Route structure, role-based view hierarchy, shared component and state design

## Route structure

| Route | Access | Component |
|---|---|---|
| `/login` | Public | `LoginPage` |
| `/instructor/*` | Instructor only | `InstructorDashboard` |
| `/student/*` | Student only | `StudentSelfCheck` |
| `/admin/*` | Admin only | `AdminPanel` (placeholder — no Admin screens built yet) |
| `*` (any unmatched path) | — | Redirects to `/login` |

Routing is handled by `react-router-dom`'s `BrowserRouter`, defined centrally in `App.jsx`. Each role gets its own top-level route namespace (`/instructor/*`, `/student/*`) rather than a shared dashboard with conditional rendering — this keeps each role's future sub-routes (e.g. `/instructor/clusters`, `/student/history`) isolated and independently extensible as 7.x/8.x add more screens.

## Role-based view hierarchy

Access control is enforced by a single wrapper component, `ProtectedRoute`, rather than scattering role checks across every page:

```
App (AuthProvider)
 └─ BrowserRouter
     ├─ /login            → LoginPage (public)
     ├─ /instructor/*      → ProtectedRoute(allowedRoles=['instructor']) → InstructorDashboard
     ├─ /student/*          → ProtectedRoute(allowedRoles=['student'])    → StudentSelfCheck
     └─ /admin/*            → ProtectedRoute(allowedRoles=['admin'])      → AdminPanel
```

`ProtectedRoute` does two checks before rendering its child:
1. Is there a logged-in user at all? If not, redirect to `/login`.
2. Does that user's role match what this route allows? If not, also redirect to `/login`.

This means role enforcement lives in exactly one place, not duplicated per-screen — adding a new role-gated screen later is just wrapping it in the same component with the right `allowedRoles`.

## Shared component & state design

**`AuthContext`** — the single source of truth for "who's logged in and as what."
- Exposes `user` (`{ id, fullName, role }`), `loading`, `login()`, `logout()`.
- The JWT itself is **not** stored in React state or context — it's kept in a module-level variable inside `api/axios.js`, set via `setAuthToken()`. This keeps the token out of React DevTools/component state entirely and out of localStorage, per the must-have that self-checks and sessions shouldn't persist tokens insecurely.

**`api/axios.js`** — single shared Axios instance used by every screen.
- Request interceptor attaches the JWT automatically — no screen manually adds an Authorization header.
- Response interceptor catches `401`s globally and force-logs-out + redirects, so expired/invalid sessions are handled in one place rather than per-request try/catch blocks.

**Why one shared instance instead of per-component fetch calls:** every future API integration task (7.5, 8.3) can just import `api` and call `api.get(...)`/`api.post(...)` without re-implementing auth headers or 401 handling — that logic is already centralized here.

## Known gaps at time of writing

- Admin role has a route and a placeholder component, but no real hierarchy or screens designed yet — mirrors the same gap noted in 0.1.2.
- No shared design-system-level components (buttons, inputs, cards) have been extracted yet — each screen currently has its own CSS file. Worth revisiting once 7.x/8.x start, since some visual duplication between `Dashboard.css` and `SelfCheck.css` already exists.
