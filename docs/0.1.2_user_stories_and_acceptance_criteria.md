# 0.1.2 — User Stories & UI Acceptance Criteria

**Scope:** Instructor and student role stories, screen-level acceptance criteria for both dashboards
cope.
## User Stories

### Instructor

1. As an instructor, I want to log in securely so that I can access my dashboard and no one else can see it.
2. As an instructor, I want to see a list of my students' submissions so that I know what's waiting for review.
3. As an instructor, I want to select a submission and see full detail — matched fragments, peer overlaps, commit/provenance flags, and the risk band — so that I have enough evidence to make an informed call.
4. As an instructor, I want to make the final originality call myself (Cleared / Under Review / Flagged) so that the system never makes that decision for me — it only flags for review.
5. As an instructor, I want to see all parties in a similarity cluster, not just one pair, so that I can catch group copying, not just 1-to-1 matches.

### Student

1. As a student, I want to log in securely so that only I can access my own self-check tool.
2. As a student, I want to submit my code (Git repo link or file upload) for a self-check so that I can catch originality issues before final submission.
3. As a student, I want to see how many self-checks I have left today so that I don't waste my quota.
4. As a student, I want to see only my risk band and general guidance — not matched files or peer names — so that I can't use the tool to identify who I'm similar to.

## Screen-Level Acceptance Criteria

### Login (1.5.1)

- Given valid credentials, the user is redirected to the dashboard matching their role (instructor / student / admin), as returned by the backend — never self-selected.
- Given invalid credentials, an inline error is shown and the user stays on the login screen.
- The JWT is held in memory only for the session — never written to localStorage or sessionStorage.
- The submit button is disabled and shows a loading state while the request is in flight.

### Instructor Dashboard (3.3 skeleton → 7.1–7.4 full build)

- Sidebar navigation is visible with Submissions, Subjects, Clusters, and Settings.
- The submission table shows, at minimum: student, subject, risk band, and status.
- Before any row is selected, the detail panel shows an explicit empty state — never blank or broken-looking.
- Selecting a row populates the detail panel with matched fragments, peer overlaps, commit/provenance flags, and the risk band.
- Final-call actions (Clear / Flag for review / Mark under review) are present on the detail panel; the decision is stored with a timestamp once wired to the backend (7.4).
- A non-instructor account cannot reach this screen — redirected to login instead.

### Student Self-Check (3.4 skeleton → 8.1–8.2 full build)

- The remaining daily quota is shown before the student submits anything.
- The form accepts either a Git repo URL or a file upload — not both required.
- The submit button is disabled once the daily quota is exhausted.
- After submitting, the result area shows only the risk band and general guidance text — no matched fragments, no peer names, under any circumstance.
- A non-student account cannot reach this screen — redirected to login instead.

## Known gaps at time of writing

These are tracked, not silently dropped:
- Admin role has no user story or acceptance criteria here yet — no Admin screen exists in the current build.
- Subject publish/unpublish and open/closed states aren't reflected in any screen yet.
