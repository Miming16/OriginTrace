
**Scope:** Design `users` and `submissions` tables; confirm fields the dashboards must read

## Method: what each screen needs to read

| Screen | Fields needed from `users` | Fields needed from `submissions` |
|---|---|---|
| Login (1.5.1) | `id`, `email`, `password_hash`, `role`, `full_name` | — |
| Instructor submission list (7.1) | student's `full_name` (joined via `submissions.student_id`) | `id`, `student_id`, `language`, `status`, `submitted_at`, risk band (from `risk_scores`, not this table) |
| Instructor filters (7.1) | — | `submitted_at` (date filter), risk band (via join), **course/section — see gap below** |
| Student self-check form (8.1) | `id` (current user) | `source_type`, `source_url`, `is_self_check`, `submitted_at` |
| Student result display (8.2) | — | `id`, `status` |

## Proposed `users` table

Unchanged from the earlier full schema — already covers every field the dashboards read:

```sql
CREATE TABLE users (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email           VARCHAR(255) NOT NULL UNIQUE,
    password_hash   VARCHAR(255) NOT NULL,
    role            VARCHAR(20)  NOT NULL CHECK (role IN ('instructor', 'student', 'admin')),
    full_name       VARCHAR(255) NOT NULL,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## Proposed `submissions` table

```sql
CREATE TABLE submissions (
    id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    student_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    source_type     VARCHAR(10) NOT NULL CHECK (source_type IN ('git', 'upload')),
    source_url      TEXT NOT NULL,
    language        VARCHAR(20) NOT NULL CHECK (language IN ('c', 'javascript', 'python', 'php')),
    is_self_check   BOOLEAN NOT NULL DEFAULT false,
    status          VARCHAR(20) NOT NULL DEFAULT 'pending'
                        CHECK (status IN ('pending', 'processing', 'complete', 'failed')),
    submitted_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

## Gap found while confirming dashboard fields

**7.1 explicitly requires filtering the instructor's submission list by "section,"** but neither `users` nor `submissions` has any concept of a course/section right now. This is the same gap flagged back when we stripped the schema down to just the 6 named 0.3 tables — the `subjects` table (and `submissions.subject_id`) got moved out at the time, but 7.1's filter requirement means it can't stay out indefinitely.

**Recommendation for 0.3.3 (Ducut, migration/constraints):** either
- (a) reintroduce a minimal `subjects` table + `submissions.subject_id` foreign key now, or
- (b) confirm this is intentionally deferred and 7.1's "section" filter will be added in a later migration once subject/enrollment work is scheduled.

Flagging rather than silently adding it back in, since it affects 0.3.1/0.3.3's work too (fingerprints/risk_scores may eventually need subject-scoping for cluster grouping in 6.2).

## Summary for handoff to 0.3.3

No column changes to `users`. `submissions` is confirmed sufficient for 8.1/8.2 (student-facing) as-is. It is **not** yet sufficient for 7.1's section filter — needs a decision before Ducut finalizes the migration.
